# tour-finder

Поиск туров из Риги (RIX), Вильнюса (VNO) и Таллина (TLL) с историей цен
и личными уведомлениями в Telegram.
Цена относится ко всему выбранному составу; покупка происходит у продавца.
Направление продукта описано в [SPEC.md](SPEC.md).
Границы текущей реализации и проверки перед платным запуском —
[балтийский пилот](docs/baltic-pilot.md).

Сборщик работает с **Join Up Baltic** и **Waavo**. Разбор источников:
[Join Up](docs/joinup-api-recon.md), [Waavo](docs/waavo-recon.md).
Незавершённый обход источника не считается подтверждением свежести данных.

## Приложение и доступ

Основной интерфейс — [Telegram Mini App](https://tour-finder-rose.vercel.app/app).
Production-бот уже создан и настроен. Просмотр туров, карточек, истории,
сохранённых поисков и уведомлений требует подписанной Telegram-сессии и
одобрения владельца. Обычная ссылка в браузере показывает экран входа.

Новый пользователь отправляет `/start`; владелец рассматривает заявку через
`/requests`. `/approved` показывает одобренных пользователей, `/deny ID`
отзывает доступ. `/stop` отключает уведомления, сохраняя одобрение и поиски.
Подробности: [контроль доступа](docs/telegram-access.md).

В приложении есть фильтры аэропортов, дат, ночей, бюджета, страны, звёзд и питания,
варианты номеров, карточка предложения и история цены. Категории питания:
RO, BB, HB, FB, AI, UAI и прочие. Архивные цены помечаются устаревшими
и не используются для новых уведомлений.

## Где работает система

| Компонент | Размещение |
|---|---|
| Web API и Mini App | Vercel, Git-интеграция репозитория, production из `main` |
| Сбор цен | GitHub Actions: [`collect.yml`](.github/workflows/collect.yml) |
| Оценка подписок и доставка | GitHub Actions: [`notify.yml`](.github/workflows/notify.yml) |
| Основные данные | Supabase PostgreSQL, серверная переменная `DATABASE_URL` |
| Архив для чтения | Зашифрованные SQLite-файлы в GitHub Releases, указатель в `archive-index` |
| Локальная разработка | SQLite `data/tourfinder.db`, если `DATABASE_URL` не задан |

Pull request запускает тесты; обновление `main` используется для production
deployment через Git. Ветка `archive-index` исключена из Vercel deployments:
публикатор добавляет запрет в её собственный `vercel.json`, поскольку эта
ветка не наследует файлы `main`. Секреты хранятся в настройках Vercel/GitHub Actions,
а не в Git, HTML или JavaScript.

Расписания GitHub Actions задают желаемую частоту, но не гарантируют
своевременного выполнения. Успешный ручной запуск не подтверждает работу cron.
Автоматическую доставку нужно проверять по реальным запускам
`schedule`/`workflow_run` и результатам worker.

## Состав туристов и сбор

Поиск не подменяет цену точного состава ценой другого количества взрослых или
детей. Поддерживаются 1–6 взрослых и до четырёх детей с возрастом 0–17 лет.
Кнопки «Запросить сбор по этим параметрам» и «Запросить свежие предложения»
сохраняют личную заявку с аэропортами, датами и остальными фильтрами.
Сохранение подписки в текущем горизонте сбора также создаёт заявку в одной
транзакции с подпиской. Более дальняя включённая подписка резервирует состав
и аэропорты, но не объявляет сбор поставленным в очередь.
`GET /api/search` ничего не собирает и не ставит в очередь. Принятая заявка
не подтверждает запуск worker, наличие предложений или срок получения.

Лимиты приёма: 20 активных заявок на владельца, отдельные 20 сохранённых поисков
и общий предел новых сочетаний «состав × аэропорт» — 12 с учётом текущих задач
и резервов подписок. Повторная заявка использует ту же запись; обновление
ограничено интервалом 15 минут. Эти лимиты не гарантируют скорость сбора.

`collect` обслуживает личные заявки сроком 21 день и действующие подписки
одобренных пользователей в горизонте 1–45 дней. Пока есть хотя бы один такой
поиск, базовые составы и старая общая очередь не создают дополнительные обходы.
При отсутствии текущих личных поисков используется первоначальное наполнение:
составы `2`, `2+1:7`, `3` и недавние общие заявки из Риги.
Каждая личная заявка сохраняет собственное сочетание состава и аэропортов;
возраста детей сортируются для сравнения. Новые заявки не вытесняют старые
ограничением «только четыре последних».

Заявки отозванных пользователей и отключённые, истёкшие или старые подписки
без владельца сами по себе заданий не добавляют. Старые общие заявки без
владельца участвуют только в первоначальном наполнении на срок 21 день и относятся к Риге;
новые API-заявки в эту legacy-очередь не записываются. Поиски без поля аэропорта
по-прежнему означают RIX.

| Ярус | Вылет через | Период обновления в планировщике |
|---|---|---|
| near | 1–7 дней | 4 часа |
| mid | 8–14 дней | 12 часов |
| far | 15–45 дней | 24 часа |

Workflow сборщика запланирован на 17-ю минуту каждого второго часа UTC.
Один запуск ограничен **6 заданиями и 50 минутами**, job — 75 минутами.
Задание определяется сочетанием источник/ярус/состав/аэропорт. Свежесть подтверждает
только законченный успешный обход; ошибки и частичные обходы остаются в очереди.
Планировщик выбирает давно не пробовавшиеся задания. Пакетная запись использует
до 200 наблюдений в PostgreSQL и 40 в SQLite; журнал отдельно показывает число
пакетов и время их записи. Источники учитывают оставшийся бюджет перед запросом
и повторной попыткой. Ограничение времени кооперативное: DNS и медленно
поступающий HTTP-ответ могут задержать завершение текущего запроса.

После первой попытки полного обхода сборщик может отложить следующее,
если оставшегося времени меньше оценки длительности: последний полный успешный
обход того же источника/яруса/состава/аэропорта за 7 дней, иначе медиана до трёх
последних полных обходов того же источника/яруса/аэропорта, плюс 20% и 30 секунд. Он может выбрать
следующее короткое задание; отложенное не считается попыткой и сохраняет
приоритет на следующий запуск. Первый полный обход получает попытку и после
короткого discovery; задания без такой истории также пробуются. Это снижает
риск частичного обхода, но не гарантирует скорость или завершение в срок.

При наличии одобренных личных поисков Waavo получает их точные фильтры через
отдельный адаптер `filtered_hotel_discovery_v1`. Задача ограничена семью днями,
одним аэропортом и оператором, восемью запросами (до 100 строк на странице) и
тремя минутами. Завершённые части учитываются по точному ключу; незавершённый
offset между запусками не переносится. Выдача минимальной цены отеля не
подтверждает полноту вариантов. В workflow допускается до 96 небольших задач
при прежнем общем бюджете 50 минут. Подробнее: [балтийский пилот](docs/baltic-pilot.md).

`assert-fresh --hours 26` проверяет все активные задания с общим пределом
26 часов; exact discovery проверяется отдельно от полных обходов. Это не
подтверждение шестичасовой свежести для отправки алерта или полноты каталога.

Для распознавания подписок владельцев оба шага сборщика получают
`TELEGRAM_ALLOWED_USER_IDS`. Этот секрет содержит администраторов;
одобрения остальных пользователей читаются из БД.

## Подписки и уведомления

Подписка поддерживает подтверждённое падение цены, попадание в бюджет или оба
события. Базовые пороги выгоды: снижение от 10% **и** €100, рейтинг от 4/5
при минимум 20 подтверждённых отзывах. Нужны устойчивая наблюдавшаяся исходная
цена, недавнее снижение и актуальный снимок не старше 6 часов. Рекламная
зачёркнутая цена не заменяет собственную историю.

Для Waavo подтверждение падения ограничено качеством идентификатора номера:
данные не считаются доказанной скидкой, если номер нельзя надёжно сопоставить.
Вкладка недавних падений использует Join Up. Попадание в бюджет само по себе
не называется скидкой.

Worker работает независимо от открытой вкладки. Расписание — минуты
`7,22,37,52` каждого часа; дополнительный запуск — после завершения `collect`
на `main` этого репозитория, включая ошибку проверки общего покрытия. Отмена сбора этот запуск не
вызывает. Перед отправкой worker повторно проверяет доступ, цену и свежесть,
применяет ограничения частоты и защиту от повторов. Без необходимых секретов
workflow пропускает оценку и доставку.

## Архив и размер базы

Архив для просмотра хранит только данные туров, историю цен и отзывы.
Это отдельный формат от аварийного бэкапа `.tfbackup`, который предназначен
для восстановления PostgreSQL. Оба формата публикуются зашифрованными;
личные данные в архив чтения не входят.

Обычный `collect` историю не удаляет. Архивирование по умолчанию выполняет
только экспорт. Очистка требует отдельного режима и явного включения;
перед удалением проверяются опубликованные файлы и неизменность живых строк.
Удаление строк не гарантирует уменьшения физического файла БД.
Настройки, формат и ограничения: [docs/history-archive.md](docs/history-archive.md).

## Локальный запуск и проверки

```powershell
py -3.12 -m venv .venv
.venv\Scripts\python -m pip install -e '.[dev]'
.venv\Scripts\python -m pytest -q
```

Локальное демо требует SQLite, отсутствующего `TELEGRAM_BOT_TOKEN`, отсутствия
Vercel-окружения и `TOURFINDER_DEMO=1`. Оно разрешает только чтение; личные записи
остаются закрыты. Перед локальным экспериментом убедись, что `DATABASE_URL`
не указывает на production.

```powershell
$env:TOURFINDER_DEMO = "1"
.venv\Scripts\python -m tourfinder.cli serve
```

Приложение откроется на `http://127.0.0.1:8000/app`. Сбор запускается отдельно
и обращается к внешнему источнику; `fetch` использует Join Up, `collect` — оба
источника:

```powershell
python -m tourfinder.cli fetch --pax "2+2:6,8" --max-pages 2 --days 14
python -m tourfinder.cli collect --max-tasks 6 --max-minutes 50
python -m tourfinder.cli stats
```

Тесты используют временные SQLite-базы и подставные источники/Telegram API.
Для аддитивной подготовки production есть `Prepare Telegram database`:
сначала `preflight`, затем `apply`; большой индекс включается отдельно.
Подготовка схемы не удаляет историю и не освобождает место.

Отзывы могут поступать из Waavo и отдельного обогащения через Google Places.
Для команды `python -m tourfinder.cli reviews --limit 50` нужен собственный
`GOOGLE_PLACES_API_KEY`; без ключа Google-провайдер не работает. Квоты и стоимость
внешнего сервиса проверяются отдельно.
