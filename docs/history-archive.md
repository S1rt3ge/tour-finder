# Архив истории туров

Архив позволяет читать ранее собранные туры после удаления их из рабочей БД
или при временной недоступности Supabase. Рабочая БД остаётся источником
актуальных цен и личных данных. Наличие workflow не подтверждает, что полный
автоматический цикл уже проверен или физическое место уже освобождено.

## Два вида архива

| Формат | Назначение |
|---|---|
| `.tfbackup` | Зашифрованный PostgreSQL dump с манифестом и проверкой восстановления; аварийное восстановление базы |
| `.tfarc` + манифест | Зашифрованные проекции туров в SQLite; чтение приложением без восстановления PostgreSQL |

Архив чтения не заменяет аварийный бэкап. Он не содержит подписок, заявок на
доступ, Telegram-пользователей, уведомлений, запросов состава или журнала
запусков сборщика. Закрытый RSA-ключ аварийного бэкапа не используется
приложением. Для `.tfarc` нужен отдельный симметричный `APP_ARCHIVE_KEY`.

## Настройки

| Настройка | Где нужна | Назначение |
|---|---|---|
| `DATABASE_URL` | GitHub Actions Secret | Явное подключение экспортёра к PostgreSQL; локальная SQLite не подставляется |
| `APP_ARCHIVE_KEY` | GitHub Actions Secret и серверное окружение Vercel | Один ключ AES-256: 32 байта в Base64 либо 64 шестнадцатеричных символа |
| `TOUR_ARCHIVE_MANIFEST_URL` | Repository Variable и серверное окружение Vercel | `https://raw.githubusercontent.com/S1rt3ge/tour-finder/archive-index/latest.json` |
| `ARCHIVE_PRUNE_ENABLED` | Repository Variable | Только `true` разрешает режим `prune` |
| `ARCHIVE_ROTATION_ENABLED` | Repository Variable | Только `true` вместе с разрешённым pruning включает ежедневный запуск |
| `GITHUB_TOKEN` | Автоматически передаётся job публикации | Публикация release и указателя; разрешение `contents: write` |

Ключ остаётся на серверах; его нельзя добавлять в клиентские переменные, Git,
манифест или логи. Сохрани резервную копию ключа отдельно от публичного архива.
Произвольная замена ключа сделает старые поколения нечитаемыми; автоматической
перешифровки и ротации ключей нет. Vercel читает публичные зашифрованные файлы
и не нуждается в GitHub-токене с правом записи.

[`archive-history.yml`](../.github/workflows/archive-history.yml) по умолчанию
предлагает ручной **export**. Режим `prune` закрыт без отдельного флага.
Ежедневное расписание — 04:17 UTC — требует обе переменные включения.
Отсутствие ключа, URL манифеста или подключения приводит к пропуску workflow
без обращения к БД. Расписание GitHub может задерживаться.

## Формат и идентификаторы

Поколение содержит каталог и **64** файла истории. Каталог хранит `hotels`,
`offers`, последние `price_snapshots`, `hotel_reviews`, `archive_offer_keys`
и метаданные. История хранит `archive_history` и метаданные. Читатель принимает
точную разрешённую схему; лишние таблицы, представления и триггеры запрещены.

Ключ предложения рассчитывается из источника, отеля, города вылета, даты,
ночей, питания, кода и размещения номера, количества взрослых и детей,
отсортированных возрастов. История распределяется по остатку ключа от деления
на 64. Числовые ID исходной базы служат только происхождением записи:
повторное использование ID не объединяет разные туры. Каталог сохраняет
своё соответствие стабильных ключей и внутренних числовых ID.

Отпечаток наблюдения включает ключ тура, время, цену, валюту, признак горящего
тура, доступность, stop-sale и среднюю цену оператора. Идентичные наблюдения
с одинаковым временем и состоянием объединяются, даже если исходные номера
снимка или запуска различались. Это история наблюдаемых состояний,
а не физическая копия каждой строки PostgreSQL.

Первый экспорт включает все имеющиеся туры и их историю. Следующие поколения
накапливают предыдущий архив: пустая рабочая база не стирает историю.
Предыдущий манифест фиксируется на весь экспорт, чтобы не смешивать поколения.
Предложение без истории или снимок без предложения останавливают экспорт;
такие строки не пропускаются молча.

## Экспорт и публикация

В заранее настроенном защищённом окружении команда имеет вид:

```console
python -m tourfinder.archive_rotation --mode export
```

Предпочтительный production-путь — ручной запуск workflow с `mode=export`.
Исходная БД только читается, но команда **публикует** зашифрованные файлы в GitHub.

1. Предыдущее поколение скачивается, проверяется и копируется локально до
   открытия транзакции PostgreSQL.
2. Данные читаются порциями внутри `REPEATABLE READ READ ONLY`. Экспортёр
   не вызывает запуск приложения или миграцию схемы. Локальный план возможного
   удаления сохраняет идентификатор snapshot и точные отпечатки строк.
3. SQLite проверяются и сжимаются; AES-256-GCM защищает содержимое и связанные
   метаданные. До любых публикаций проверяется вместимость **всех 65 файлов**.
4. Создаётся release `archive-history-<generation>`. Старые поколения и
   аварийный бэкап не изменяются. Все загруженные файлы скачиваются обратно:
   проверяются SHA-256, GCM, схема, SQLite integrity, идентичность и число строк.
5. Полный манифест публикуется после проверки файлов. Он содержит каталог
   и все 64 части истории, размеры, контрольные суммы и число строк.
6. `archive-index/latest.json` обновляется с проверкой прежнего Git commit
   и без принудительной перезаписи. Указатель перечитывается через API и
   публичный raw URL. Устаревший ответ кэша блокирует последующее удаление.

Открытые SQLite и план удаления остаются в приватном временном каталоге runner
и не загружаются как artifacts. Логи содержат фазы, размеры и агрегаты;
прогресс предложений и истории выводится каждые 250 000 строк. Неудача может
оставить непривязанное зашифрованное поколение в Releases, но оно не разрешает
очистку и не заменяет предыдущий рабочий указатель.

## Ограничения размера и чтения

| Ограничение | Значение |
|---|---|
| Открытый каталог | 320 MiB |
| Одна открытая часть истории | 32 MiB |
| Кэш открытых SQLite | 384 MiB |
| Временные файлы читателя | 480 MiB |
| Проверка одного SQLite | Ограничение времени 30 секунд |

Для каждого файла требуется
`2 × размер ciphertext + размер открытого SQLite ≤ 480 MiB`.
Это учитывает одновременно зашифрованный файл, проверенные сжатые данные
и распакованную базу. Проверка выполняется до публикации и при чтении;
одного ограничения каталога недостаточно. Занятые запросом файлы не вытесняются
из кэша. Превышение лимита даёт отказ, а не неполную копию.

Границы не подтверждают фактическую задержку холодного запуска Vercel.
Скачивание, распаковку и проверку большого каталога нужно измерять
на реальном поколении. Тайм-аут нельзя увеличивать без измерения.

Поиск предпочитает рабочую БД и дополняет недостаточную выдачу архивом.
При доступной БД совпадающий живой тур подавляет архивную цену, даже если
актуальная цена уже не проходит бюджет. История объединяется по устойчивому
ключу и отпечаткам. Единственная последняя цена в каталоге не выдаётся
за статистику всей истории. Архивные карточки всегда `stale`; уведомления
используют только рабочую БД и повторно проверяют свежесть.

Архив подчиняется тому же Telegram-контролю. Владелец с валидной подписью
может читать архив при недоступной БД. Для остальных пользователей
невозможность проверить одобрение закрывает доступ. Публичный ciphertext
не делает поиск анонимным.

## Отдельная очистка

```console
python -m tourfinder.archive_rotation --mode prune --max-snapshots 50000 --max-offers 5000
```

Команда требует `ARCHIVE_PRUNE_ENABLED=true` и сначала выполняет полный
экспорт с проверкой публикации. При размере рабочей БД менее **350 MiB**
очистка пропускается. Ориентир освобождения — **300 MiB**, рассчитанный по
среднему размеру строк и индексов. Это оценка повторно используемого места,
а не измеренное уменьшение файла на диске.

Для предложений с ещё не прошедшей датой вылета сохраняются последние **14 дней**, первый
и последний снимки и обе стороны каждого изменения полного состояния цены.
Так сохраняются границы устойчивых цен, начало снижения и изменения stop-sale.
Удаляются только старые внутренние точки одинакового состояния.

Предложение с прошедшим вылетом можно удалить вместе с историей, только если
всё уже представлено в проверенном архиве, метаданные и каждый снимок остались
неизменными, новых снимков нет и предложение не связано с алертами. Перед
удалением строки повторно читаются с блокировками; удаляются точные ID из
локального плана. Новая цена, исправленная запись или уведомление защищают
всё предложение от удаления в этом запуске.

По умолчанию предел — 50 000 снимков суммарно, 5 000 просроченных предложений
и 10 минут очистки. Это ограничение одной попытки, а не обещание достигнуть
целевого размера за день. Блокировки имеют короткий тайм-аут; ошибка
откатывает текущую транзакцию. Отели, отзывы, журналы запусков и личные таблицы
этой очисткой не удаляются.

Для разового обслуживания есть ручной `mode=prune`, `maintenance=true` в
workflow, либо команда в том же защищённом окружении:

```console
python -m tourfinder.archive_rotation --mode prune --maintenance
```

Она сохраняет требование `ARCHIVE_PRUNE_ENABLED=true`, но повышает пределы до
300 000 предложений, 3 000 000 снимков и 15 минут очистки. Один проверенный
экспорт используется для всех пакетов: до 250 предложений и 5 000 снимков
на пакет, отдельное крупное предложение — до 10 000 снимков. Лимиты удаления
расходуются только подтверждёнными коммитами. Более крупные предложения
пропускаются. Общий job ограничен 45 минутами; очистке выделяется не больше
остатка до 42-й минуты процесса. Это предел работы, а не гарантия достижения
целевого размера. Расписание не может включить `maintenance`.

Архивирование, сбор и восстановление сборщика используют общую concurrency
группу `collect`, без отмены уже работающего запуска. При ручном обслуживании
нужно проверить, что нужный запуск действительно начался: в стандартной
очереди GitHub Actions новый ожидающий запуск может вытеснить предыдущий
ожидающий запуск этой группы. Уведомления используют отдельную очередь;
проверка ссылок из алертов и блокировки при очистке сохраняются.
[Правила очереди GitHub Actions](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/control-workflow-concurrency).

Режим не выполняет `VACUUM FULL`, `TRUNCATE` или сброс последовательностей.
Удалённые строки могут оставить свободные страницы внутри прежнего файла.
Физическое уменьшение БД требует отдельного измерения и при необходимости
обслуживания с проверкой свободного диска и блокировок. Старую команду
`tourfinder.cli prune` нельзя использовать вместо этой процедуры:
она не проверяет опубликованный архив.

## Физический размер после очистки

Ручной workflow `Maintain tour storage` по умолчанию выполняет только
`preflight`: размеры таблиц и индексов, точные количества строк, активность,
блокировки, доступные сведения о WAL и запас места, необходимый по принятому
консервативному расчёту. SQL-тексты сессий, строки данных и секреты не выводятся.

Операции `replace-index`, `vacuum-offers` и `vacuum-snapshots` требуют успешной
проверенной очистки и отдельного свежего измерения свободного диска в Supabase
Dashboard. Вводятся `verified_prune=true`, `disk_free_mib` и время измерения
`disk_measured_at` в UTC, не старше десяти минут. Один запуск выполняет одну
операцию; автоматических повторов и принудительного завершения сессий нет.

Порядок обслуживания: создать и проверить индекс
`idx_snapshots_latest(offer_id,fetched_at,id)`, затем удалить старый точный
префиксный индекс `idx_snapshots_offer`; при необходимости отдельно уплотнить
`offers`, заново измерить свободное место и отдельно уплотнить
`price_snapshots`. Сначала проверяются имена, определения и состояние индексов.
Неподходящий или незавершённый новый индекс не позволяет удалить старый.

Скрипт использует session pooler существующего проекта на порту 5432, чтобы
проверенные тайм-ауты оставались на той же сессии. Блокировка ожидается максимум
три секунды, построение индекса — до пятнадцати минут, переписывание одной
таблицы — до десяти. `VACUUM FULL` временно требует эксклюзивную блокировку
таблицы: запросы к ней могут завершаться по тайм-ауту, поэтому операции следует
проводить в окно обслуживания. До и после сравниваются количества строк и
состояние индексов. Отсутствие необходимых прав или сведений о WAL блокирует
применение, сохраняя возможность диагностики.

Запас места — проверка с резервом, а не гарантия пикового потребления:
для переписывания таблицы требуется два её текущих полных размера плюс
128 MiB. Успешное удаление строк и успешное физическое уменьшение базы
проверяются отдельно; целевой размер нельзя подтверждать одним статусом
завершения архивного workflow.

## Проверка перед включением расписания

Сначала выполнить экспорт, проверить манифест и чтение каталога, карточки
и истории через Mini App. Отдельно проверить недоступность БД и контроль
доступа. Затем провести ограниченную ручную очистку, сравнить агрегаты
и убедиться, что удалённая из БД история читается из архива. Только после
этого включать обе переменные ежедневной ротации и наблюдать реальные
успешные scheduled runs. Не выводить ключи или подключения для диагностики.
