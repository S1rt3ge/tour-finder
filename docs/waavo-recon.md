# Разведка: Waavo API (`joinastra.waavo.com`)

## Исправление от 2026-10-09: контракты поиска были смешаны

Этот раздел заменяет технические утверждения ниже о параметрах и полноте
поиска. Старый текст сохранён как история разведки, а не текущий контракт.

В двух production-обходах для непересекающихся периодов 17–23 октября и
24 октября–23 ноября сохранились одни и те же 5 673 предложения. Их реальные
даты лежали между 2026-10-10 и 2027-06-19; соответственно 4 781 и 3 203 строки
оказались за пределами запрошенного периода. Даты предложений не подменялись,
но успешный обход ошибочно служил доказательством покрытия запрошенных дат.

Причину уточнили по официальной странице `/travels_search` и её
[JavaScript-клиенту Waavo](https://joinastra.waavo.com/cdn/travels-search/index.js?v=fd7dbe94).
SHA-256 сохранённого bundle (UTF-8, LF):
`fd7dbe946972469c9eda0abf3b4dc42b3ef736fce98fb459f44e11c6433e5c2a`.
Сторонний bundle в репозиторий не включён.

### Два разных контракта

- `/api/v1/travels/search` официальный frontend вызывает через **POST** для
  поиска отеля: `cityId`, `hotelId`, одна `departureDate`, `departureAirport`,
  `durationFrom`, `durationTo`, `language`, `rooms`, `cacheStrategy="none"`,
  `calculateAdvance=true`. В указанном bundle это построитель `Wte` и вызов
  `qI.SEARCH_V1`. Подтверждённого контракта общего GET с `dateFrom/dateTo` здесь нет.
- `/api/v1/cheap_travels_search/` используется для поиска предложений по
  диапазонам. Построитель `uje` передаёт перечисленные ниже фильтры; `cje`
  выполняет первоначальный GET и продолжение через POST.

| Критерий | Параметры первоначального GET |
|---|---|
| Вылет и состав | `departureAirport[]`, `adults`, `children`, `childrenAges[]` |
| Даты и ночи | `dateFrom`, `dateTo`, `durationFrom`, `durationTo` |
| Питание и звёзды | `mealGroupFrom`, `hotelRating` |
| Отзывы | `tripAdvisorRatingFrom` |
| Направление | `countryId[]`, `cityId[]` |
| Цена за весь состав | `priceFrom`, `priceUntil` |
| Цена на человека, отдельный режим frontend | `pricePerPersonFrom`, `pricePerPersonUntil` |
| Оператор | `operator[]` |
| Страница | `offset`, `limit`, `lastListPrice`, `excludeHotelIds[]` |

В JSON для POST массивы передаются под именами без `[]`. Frontend разделяет
выдачу по операторам; cursor каждой такой выдачи содержит число уже полученных
строк, цену последней строки и список полученных hotel IDs. Он увеличивает
`offset` на фактическое число строк и считает выдачу исчерпанной только после
**пустого** ответа, а не после страницы короче `limit`.

Один ограниченный проверочный GET второго endpoint с `limit=3`, RIX,
одним взрослым, датами 2026-10-17…2026-10-23 и 2–21 ночью вернул HTTP 200 за
7,375 с. Все три строки соответствовали составу, аэропорту и диапазонам:
вылет 17 октября, 3 ночи, EUR, питание RO/RO/BB. Ответ имел вид
`{"results": [...], "request": []}` без total/pages или признака завершения.
Строки плоские: реальные `offerKey`, `hotelId`, `date`, `duration`, состав,
`departureAirportCode`, `price`, `currency`, `mealGroupCode`, отзывы и `link`.
Этот небольшой запрос подтверждает работу выбранных параметров, но не полноту
всей выдачи и не одинаковое поведение всех операторов.

### Уточнение параметров и новый адаптер

Дополнительный одиночный GET официального
`/travels_search/cheap_travels_filters?language=lav` 9 октября вернул список
операторов `anextour`, `coral`, `joinup`, `novaturas`, `teztour`, питание
`RO`, `BB`, `HB`, `AI` и длительность 2–21 ночь. SHA-256 ответа:
`437b9cda9363e706eb10ecbe26f7291559ea8b0ced80448dc17bee0339d5ec8f`.
Компонент `Nhe` официального bundle добавляет к варианту питания подпись
`and better`: это нижняя граница. Для еды BB/HB/FB/AI/UAI достаточно запроса
с `mealGroupFrom=BB`; для FB используется HB, для UAI — AI с точной локальной
проверкой результата. Неподтверждённые значения FB/UAI напрямую не передаются.

Коды стран этого endpoint имеют отдельный смысл: например, TR=15, EG=18,
CY=56. Старое отображение ID 18 в legacy-инвентаре как Турции нельзя переносить
в новый запрос. Планировщик использует подтверждённую карту нового endpoint;
неоднозначный старый raw ID не расширяется молча до другой страны.

Frontend объединяет строки до минимальной цены отеля; cursor исключает уже
полученные hotel IDs. Это поиск предложений отелей, а не доказательство всех
вариантов комнаты, питания и даты. Официальный интерфейс обозначает питание,
звёзды и рейтинг как нижние границы (`and better`); локальная проверка выбранных
фильтров обязательна. Фильтров room code/name и нескольких номеров в этом
построителе нет.

Новый адаптер — отдельный режим
`filtered_hotel_discovery_v1`: точные аэропорт, состав, даты и ночи заявки;
питание, звёзды, известные source IDs стран и общий бюджет передаются upstream
до выбора минимальной цены. Все критерии повторно проверяются локально.
Несколько выбранных питаний не превращаются в CSV: передаётся нижний
поддерживаемый порог, а исходный выбор категорий и raw-кодов остаётся точным
локальным пересечением. Каждому оператору соответствует отдельный первый GET
с `operator[]`, затем POST с тем же оператором и собственным cursor.
Работа ограничивается числом запросов и временем; незавершённый cursor не
означает отсутствие предложений. Полнота общего каталога остаётся неподтверждённой.

Адаптер сохраняет реальные поля и идентичность предложения, не придумывая
отсутствующие аэропорт прилёта или условия комнаты. Неполные условия (`wu2`)
остаются непригодными для исторических сигналов скидки. Ответ должен явно
подтверждать состав, аэропорт, дату, ночи, EUR и положительную общую цену.
HTTP 403/429 прекращает дальнейшие Waavo-запросы этой попытки workflow.

Завершение части означает только пустой ответ после обхода её потока.
Короткая страница, повтор страницы, лимит запросов или времени завершением
не считаются. `tier=demand`, `query_key` и `discovery_complete` сохраняются
в существующем журнале. Части имеют устойчивые абсолютные даты; незаконченная
пагинация начинается заново, а завершённые части пропускаются до срока обновления.
Даже успешная часть не получает `inventory_contract` и не заполняет общий
coverage каталога.

В защитном исправлении сборщик проверяет фактические даты и ночи каждого
ответа, включая исключаемых операторов. Первое нарушение прекращает пагинацию;
предыдущие корректные строки сохраняются, нарушившая строка пропускается,
обход остаётся incomplete. Новые Waavo-обходы записывают
`scope_validation="response_date_nights_v1"`. Для доказательства полного
инвентарного покрытия дополнительно нужен точный контракт
`inventory_contract="bounded_inventory_v1"`, который текущий GET-клиент
не записывает. Даже пустой успешный ответ или случайно подходящие даты
не превращают старый endpoint в подтверждённый поиск по диапазону.
Такие обходы не обновляют свежесть и эталон длительности полного сбора;
их попытки сохраняются для справедливого порядка очереди.
Проверки scope и коллектора: **107 тестов прошли**
на временных SQLite-базах и подставных страницах; это не проверка deployment.

## Историческая разведка от 2026-07-18

> Дата: 2026-07-18. Источник найден через astrature.lv (агрегатор всех балтийских
> операторов). Astrature = обёртка вокруг **Waavo** — движка поиска туров, который
> отдаёт ВСЕХ операторов одним чистым JSON API. Без авторизации, без бот-блока.

## TL;DR — это лучший источник из всех

Один REST JSON API возвращает офферы **всех операторов сразу** (в одной выдаче видел
teztour, novaturas, joinup, coral, anextour), плюс встроенные **TripAdvisor-рейтинги**,
**цену было/стало** и **дип-линки**. Превосходит наш нынешний Join Up (один оператор)
по всем статьям и делает ненужными отдельные модули Novatours/Tez/Anex/Coral.

## Доступ

- Хост инстанса astrature: **`https://joinastra.waavo.com`** (из `data-host` виджета).
  У каждого партнёра Waavo свой сабдомен; astrature = `joinastra`.
- **Без авторизации, без куки, без бот-защиты.** Обычный GET + `Referer`, отдаёт JSON.
- Astrature встраивает Waavo через iframe (`waavo_loader.min.js` → `iframe6.min.js`),
  но API дёргается напрямую.

## Эндпоинты (проверены живьём)

| Endpoint | Назначение |
|---|---|
| `GET /api/v1/travels/search` | Полный поиск. `data.offers[]` (вложенная структура) |
| `GET /api/v1/cheap_travels_search/` | **Горящие / last-minute** — наш кейс. `results[]` (плоская) |
| `GET /api/v1/travels/offer/details` | Детали оффера (по offerKey) |
| `GET /api/v1/hotel/details` | Детали отеля |
| `GET /travels_search/cheap_travels_filters?language=%language%` | Значения фильтров |

## Параметры поиска (из бандла `cdn/travels-search/index.js`)

`departureAirport` (код, напр. `RIX`; можно список через запятую), `dateFrom`,
`dateTo`, `adults`, `children`, `childrenAge`, `durationFrom`, `durationTo`,
`mealGroupFrom` (BB/HB/AI/RO), `operator` (список), `country`/`countries`, `stars`,
`tripAdvisorRating`, `segments`, `outboundTime`, пагинация `page`/`offset`/`limit`.
Одна страница = 100 офферов.

## Структура оффера (`cheap_travels_search` results[])

```
offerKey, operatorCode (novaturas|joinup|teztour|coral|anextour|itaka|...)
hotelId, hotelName, hotelRating (звёзды), hotelLatitude, hotelLongitude
tripadvisorRating, tripadvisorRatingsCount   ← ОТЗЫВЫ ВСТРОЕНЫ (наш v3 даром)
roomName, mealGroupCode (BB/HB/AI/RO), mealTranslation
countryName, countryId, cityName, arrivalCityId
departureAirportCode, departureAirport
adults, children, childrenAge[], date (вылет), duration, tripDuration
price, priceBefore  ← БЫЛО/СТАЛО ВСТРОЕНО, pricePerPerson, currency
transferIncluded, totalOrders, images[]
link (дип-линк на astrature→оператор с проброшенными параметрами)
```

`/api/v1/travels/search` — та же инфа, но вложенно: `offer.hotel{...tripadvisor...}`,
`offer.room.meal.group.code`, `offer.region.country`, `offer.operator.code`,
`offer.pricing{price, priceBefore, currency}`, `offer.hotelUrl`, `offer.reservationUrl`.

## Почему это меняет всё

| | Join Up (текущий) | **Waavo** |
|---|---|---|
| Операторов | 1 | **все сразу** (5+) |
| Страны | 8 | все, что летают операторы (шире) |
| Отзывы | нет (v3 не сделан) | **TripAdvisor встроен** |
| Было/стало | считаем сами | **`priceBefore` встроен** |
| Дип-линк | сами собирали | **`link` готов** |
| Доступ | открытый REST | открытый REST (так же легко) |
| Матчинг отелей между операторами | — | `hotelId` от Waavo единый → **сравнение цен на один отель у разных операторов из коробки** |

## ⚠️ ВАЖНО: Waavo НЕ полный по каждому оператору

Проверено на практике (наблюдение пользователя 2026-07-18): конкретный тур, который
есть **напрямую у Join Up**, в выдаче astrature/Waavo **НЕ показывался**. Агрегатор даёт
широту (все операторы), но жертвует полнотой по каждому: кеширует реже источника,
роняет часть офферов (динамические пакеты, отдельные комбинации номер/питание/отель),
возможны задержки обновления. То есть Waavo — **не строгое надмножество** Join Up.

## Риск

Тот же класс, что и Join Up: неофициальный API, может смениться/закрыться. Плюс
зависимость от посредника (Waavo/astrature), а не от самих операторов, И неполнота
выдачи (см. выше). Смягчение: вежливый троттл, бережный сбор.

## Вывод / рекомендация (пересмотрено)

**Не заменять Join Up, а добавить Waavo ВТОРЫМ источником.** Раз Waavo неполон:

- **Join Up direct остаётся** — полное покрытие этого оператора (включая туры, которых
  на агрегаторе нет).
- **Waavo добавляем ради ОСТАЛЬНЫХ операторов** (Novatours, Tez, Anex, Coral) — их
  никак иначе дёшево не взять, плюс TripAdvisor-отзывы и было/стало.
- Чтобы не задваивать Join Up: тянуть Waavo со ВСЕМИ операторами КРОМЕ joinup
  (joinup берём напрямую, он полнее). Либо при задвоении оффера предпочитать
  Join-Up-direct как авторитетный.

Итог: полный Join Up + широкое покрытие остальных. Пайплайн переиспользуется как есть;
новый модуль `sources/waavo.py`, поле `source` в схеме уже поддерживает несколько
источников. Отзывы Waavo (TripAdvisor) можно лить в нашу `hotel_reviews` — закрывает v3
для не-joinup отелей даром.
